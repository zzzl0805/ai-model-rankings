# v1.4 模型档案与信息架构重构

> 状态：🚧 v1.4.0 已上传（2026-11-21），待提审/发布
> 创建日期：2026-11-21
> 最后更新：2026-11-21
> 触发：用户反馈「详情页对陌生模型介绍不够（公司/历程/重大事件/专业规格）」+「我的和规则挤在右上角不合适」

## 1. 背景与需求判断

### 1.1 用户反馈

1. 点进一个陌生模型（如 Gemini），不知道：哪家公司、发展历程、重大事件、专业规格。
2. 首页右上角「我的」和「规则」挤在一起不合适；用户预期「我的」在底部（tabBar）。

### 1.2 判断：需求合理，但要分层收敛

**合理**：详情页是分享/搜一搜的主要落地页。陌生用户的第一组问题是「谁家的、什么来头、能干什么、值不值、有没有替代品」。现在详情页只能回答「排第几、多少钱」，无法支撑选型。

**需要收敛**：
- 「公司/规格/排名/同价位竞品」是**结构化事实**，可以规模化、自动化。
- 「发展历程/重大事件/适合谁」是**编辑型知识**，任何榜单数据源都没有；不能靠爬虫或让模型自由生成，否则会出现无法追溯的错误。
- 689 个模型全部做百科不现实。应按「头部深、长尾浅」分层：Top 30–50 全档案，Top 150 基础档案，长尾只展示自动事实并明确标注「档案建设中」。

### 1.3 这是哪类数据问题

**不是数据量/抓取频率问题，再加 4000 行同类榜单也不会变好。** 是四层问题：

| 层 | 问题 | 本质 |
|---|---|---|
| 主数据（实体） | 4193 行是 `(类目, 维度, 模型名)` 事实行，没有 model/company/family 实体；283/689 个名字带 `(High)/(Max)/Thinking` 变体，同一底层模型被拆散 | 缺星型模型：事实表 + 维表 + 别名桥 |
| 非结构化内容 | 发布历程、重大事件、优缺点、适用场景，LMArena / 定价源都不提供 | 内容供给与编辑流程缺失 |
| 数据治理 | 价格单位/币种/来源/日期不完整；context 45% 为空且格式混杂；Agent 榜是 0–30 的净提升率却叫 Elo | 缺 provenance 与语义约束 |
| 信息架构 | 「我的」是目的地型入口，却放在右上角与胶囊/规则竞争，点击区仅约 15–20px，随 400+ 行列表滚走 | 导航与入口位置问题 |

### 1.4 现状数据审计（2026-11-21）

- 4193 行、689 个不同模型名；283 个带括号变体；平均 1.76 个类目。
- 厂商：445/4193 行 provider 为空；63 个模型全程无厂商；50/689 最终显示「其他」。
- 价格：365/689 个模型没有任何价格；text-to-image 85 个中 77 个无价；只有 `$input/output per M token` 一种计价语义。
- 上下文：45.1% 行为空；有值的格式混杂（`1048K`、`1M`、`0<Token≤1M`、`262.1K`）。
- 展示名：`NAME_MAP` 仍按旧 slug 匹配，689 个里只命中 10 个；其余直接显示 arena 原始名。
- 评分语义：`agent` 类目实际是净提升率（0–30.35），字段叫 `elo`，详情页按 Elo 展示/画条。
- 跨类目 Elo 不可比（text 中位 1360 / webdev 1474 / image-to-webdev 1540），不能放在同一套能力条里比较。
- 排名变化：`delta/isNew` 计算逻辑存在，但当前落盘为 0 行；没有 firstSeen / 7 日 / 30 日趋势。

结论：详情页不是「文案写少了」，而是缺少**模型实体层**，只能把若干榜单行按名字拍平。

## 2. 目标与验收标准

### 2.1 目标

把详情页从「排行榜的一行」升级为「模型决策卡 + 轻档案」：
用户 3 分钟内能判断：**这是谁、什么来头、能干什么、多少钱、和谁比、值不值得用**。

### 2.2 验收标准

- [ ] Top 50 模型具备完整档案：公司、系列/代际、发布日、模态、上下文、最大输出、许可证、3 条以上历程事件、优缺点、同系列/竞品，全部带来源与更新时间。
- [ ] 100% 模型：不再出现「其他」厂商；显示名可读；能看到所在类目的排名与百分位；价格有单位和来源；Agent 榜不再标 Elo。
- [ ] 详情页信息分区清晰，支持公司页/系列页跳转；长尾模型有诚实的「档案建设中」降级。
- [ ] 「我的」成为底部 tabBar 第 5 项常驻入口，右上角只保留页面级动作。
- [ ] 指标：详情页停留/滚动深度、详情→收藏率、详情→对比率、档案覆盖率、数据纠错反馈数。

## 3. 方案

### 3.1 数据模型：从宽表到星型模型

```
fact_ranking (现有 4193 行 + 派生)
  ├─ modelId / variantId        ← 通过 alias 桥接
  ├─ scoreType (elo | net_improvement)
  ├─ rank / total / rankPct / votes / margin / delta / firstSeen
  └─ catId / dimId / name（保留，向后兼容）

dim_company
  id, name, nameZh, parent, country, founded, hq, founders[],
  website, summary, sources[{url, retrievedAt}]

dim_family
  id, companyId, name, nameZh, description,
  generations[], predecessorFamilyId, successorFamilyId, sources[]

dim_model
  id, familyId, companyId, displayName, displayNameZh, aliases[],
  variantOf, releaseDate, status(ga|preview|deprecated),
  modalities{input[], output[]}, contextTokens, maxOutputTokens,
  paramsTotalB, paramsActiveB, architecture, openWeights, license,
  knowledgeCutoff, apiModelIds[], docsUrl, modelCardUrl,
  summary, strengths[], limitations[], bestFor[], notFor[],
  sources[], verifiedAt

bridge_alias
  rankingName | pattern → modelId, variantLabel,
  matchMethod(exact|regex|manual), confidence

fact_event
  id, date, scope(company|family|model), refId,
  type(release|update|price_change|deprecation|award|incident|acquisition),
  title, summary, importance(major|minor), sourceUrl, retrievedAt

fact_price
  modelId, unit(token|image|video_second|audio_minute|request),
  amount, currency, tier(standard|cached|batch),
  source, sourceUrl, asOf, matchedOpenRouterId, isProxy
```

构建产物：

- `model_catalog.json`：companies + families + models + aliases + events，合并为按 modelId 索引。
- `model_index.json`：每模型聚合的类目排名/百分位、最佳类目、上榜类目数、同价位竞品、context/price 归一化。
- `model_history.json`：从每日 tag 派生 firstSeen、delta1d/7d/30d、bestRankEver。

**存放方式**：不并入 `rankings.json`（避免主包和 1MB 返回限制）。catalog 单独上传云存储，数据库加一个 `_id='catalog'` 指针；详情页首次打开懒加载并本地缓存，长尾/弱网回退到现有基础信息。Top 50 catalog 预计 <200KB，主包不膨胀。

### 3.2 数据来源：自动化与编辑分开

| 数据 | 来源 | 方式 | 覆盖 |
|---|---|---|---|
| 排名/Elo/票数/置信度 | LMArena（现有） | 每日自动 | 全量 |
| 上下文/模态/最大输出/supported_parameters/描述/创建时间/缓存价 | OpenRouter `/api/v1/models`（已实测：476 个模型，字段含 context_length、architecture.input/output_modalities、top_provider.max_completion_tokens、created、description、knowledge_cutoff、links、pricing） | 每日自动；pipeline 已在请求，目前只用了价格和 context，其余丢弃 | 命中 OpenRouter 的 ~224 个；其余回退官方文档/人工 |
| 许可证/是否开源 | 上游 `rawName` 的 `· License` 尾巴（89.4% 行有） | 构建时解析并落盘 | 全量可解析部分 |
| 参数量/架构 | HuggingFace API / 模型卡（开源模型） | 周更半自动 | 开源模型 |
| 公司简介/成立/总部/系列代际 | 官方 About/新闻稿/模型卡 | 人工 + LLM 起草（必须附来源） | Top 50 先做 |
| 发展历程/重大事件 | 官方发布博客/定价页/新闻 | 编辑型；LLM 起草草稿，人工审核后入 `events.json` | Top 50 每模型 3 条以上 |
| 优缺点/适合谁/不适合谁 | 编辑部综合官方说明 + 独立评测 | 人工审核；禁止无来源断言 | Top 50 |

原则：
- 每条断言必须能点回来源；`verifiedAt` 过期（如 >6 个月）在页面提示「信息可能过时」。
- 明确区分「厂商官方口径」与「独立盲测/第三方数据」，不混在一句话里。
- 不用 LLM 直接生成事实；只用于**基于已抓取官方页面的草稿**，且必须保留引用。

覆盖策略：
- Tier 1（Top 30–50，按榜单头部 + 访问量）：全档案 + 历程 + 优缺点 + 同系列/竞品。
- Tier 2（Top 150）：结构化档案 + 1–3 条关键事件。
- 长尾（其余 500+）：自动事实（公司/规格/排名/价格）+「档案建设中」，不编内容。

### 3.3 详情页信息架构

建议分区（自上而下）：

1. **身份卡**：模型名 + 变体标签、公司（可点进公司页）、系列/代际、发布日、状态（正式/预览/下线）、开源/闭源、许可证、主榜名次徽章（非文本模型显示「文生图第 N 名」）。
2. **一句话定位 + 适合/不适合**：3 条 strengths、3 条 limitations、bestFor/notFor。
3. **关键规格**：上下文、最大输出、输入/输出模态、参数量（开源）、知识截止、API Model ID、官方文档/模型卡链接。
4. **多榜表现**：每个上榜类目的排名/百分位/样本量；最佳类目、最弱类目；明确「跨类目 Elo 不可直接比较」；Agent 显示「净提升率 %」而非 Elo。
5. **价格**：按计价单位展示（per M token / per image / per second / per request）；区分官网价、OpenRouter 代理价、缓存/批量价；标注 asOf 与币种。
6. **同系列与竞品**：同 family 其他版本；同价格带 ±20% + 同类目排名相近的 3 个替代模型。
7. **发展历程**：模型/系列/公司事件时间线，带来源；长尾无事件则隐藏。
8. **来源与纠错**：数据来源、更新时间、纠错入口。

长尾降级：只显示 1、4、5 和自动规格，用「档案建设中」说明，不显示空白模块。

### 3.4 导航与信息架构

**推荐 A：加第 5 个 tab**：排行 / 对比 / 计算器 / 推荐 / 我的。

- 「我的」是目的地型入口（收藏/对比组/计算记录），平台惯例是底部最右；原生 tabBar 有选中态、无障碍和底部安全区。
- 当前右上角入口实测点击区约 15–20px 高，低于微信 20px 体验下限；header 不 sticky，滚动 400+ 行后消失。
- 5 个纯文字 tab 在 375px 下每格 75px，2–3 字标签不截断；官方允许 2–5 个（设计指南建议 ≤4，需要上线后看误触和大字号）。
- 同步改造：
  - 首页 header 删除「我的」「规则」，只留标题和数据日期；列头 ⓘ 保留。
  - 「规则/评分方法论」「关于」「隐私」「导出」收进「我的」页底部，「规则」不再是无归属的顶栏链接。
  - 「我的」去掉返回按钮（tab 页无返回语义）。
- 备选 A′：若 5 tab 明显拥挤，把「推荐」并入排行/我的，保留 4 tab（排行/对比/计算器/我的）；不要退回右上角或右下角悬浮按钮。
- 否决 B（悬浮按钮）：会遮挡列表右侧 75px 的 Elo/票数列，且与详情页 compare-bar、海报弹层 z-index 冲突。
- 否决 C（维持右上角）：入口仍小、仍滚走，只是把两个链接减成一个。
- 需要同步更新 v1.3 文档里「不加第 5 个 tab」的决策，并补一条 ADR。

## 4. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 编辑内容错误/过时 | 公信力受损 | 每条带来源与 verifiedAt；过期提示；纠错入口；宁可缺失不编造 |
| 维护成本失控 | 689 个模型做不完 | 头部深、长尾浅；只对 Top 50 做时间线；自动事实优先 |
| 数据源 ToS/许可 | 法律风险 | 遵守 OpenRouter/HF 条款，注明来源，不整段转载 |
| 跨类目 Elo 误读 | 选型错误 | 只用类目内百分位，不做跨类目平均；页面明确说明 |
| 包体积/1MB 限制 | 详情页打不开 | catalog 独立云文件 + 懒加载 + 本地缓存；不并入 rankings |
| 范围蔓延成百科 | 偏离排行榜定位 | v1.4 只做「决策卡 + 轻档案」，不做全站知识库 |
